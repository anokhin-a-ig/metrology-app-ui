# Design

## Context

См. `proposal.md` — Why. Текущее состояние, влияющее на решение:

- `DepartmentsPage` хранит текущую страницу корня, `expanded` и кэш `childrenByParent`; обновление после создания должно вписаться в эту модель.
- Бэкенд уже принимает `POST /api/v1/departments` с `{ name, type, parentId? }`. После исправления `@RequestBody` создание работает.
- БД — PostgreSQL 15 с `lc_ctype = C`. Обычные `lower()`/`ILIKE` не сворачивают регистр кириллицы; ICU-коллация `ru-RU-x-icu` доступна и работает корректно.
- Уникальный индекс БД `uc_department_name` учитывает регистр. На уровне приложения уже есть проверка `existsByNameIgnoreCase`, но она использует коллацию по умолчанию и для кириллицы фактически не работает.
- `searchByName` возвращает полный `DepartmentResponseDto` и вызывает ленивые `children`/`parent` для каждой строки, давая N+1.
- Основная спека `department-catalog` восстановлена из архивного delta, чтобы новый change был MODIFIED/ADDED поверх существующего поведения.

## Goals / Non-Goals

**Goals:**

- Добавить создание департамента из UI без перезагрузки страницы.
- Сделать регистронезависимые уникальность и поиск по имени корректными для кириллицы.
- Убрать N+1 из поиска и сохранить быстрый отклик combobox.
- Обновлять дерево точечно, сохраняя раскрытые узлы и текущую страницу корня.

**Non-Goals:**

- Редактирование и удаление департаментов.
- Изменение правил иерархии типов: родителем может быть любой департамент, поле обязательно только для не-`FACTORY`.
- Глобальная оптимизация N+1 в постраничной таблице; правим только поиск.
- Полноценный UI-kit или добавление сторонних библиотек.

## Decisions

### 1. Регистронезависимая уникальность через функциональный ICU-индекс

Обычный `lower(name)` в текущей БД не меняет кириллицу из-за `lc_ctype=C`. Поэтому:

```sql
CREATE UNIQUE INDEX ux_department_name_lower_icu
ON department (lower(name COLLATE "ru-RU-x-icu"));
```

Старый `uc_department_name` оставляем: он не мешает, а его удаление не требуется для работы. Индекс создаётся новой Liquibase changeset с precondition, которая проверяет отсутствие существующих case-дубликатов.

Запросы должны использовать ту же коллацию, иначе индекс не поможет:

```sql
lower(d.name COLLATE "ru-RU-x-icu") =
lower(CAST(:name AS text) COLLATE "ru-RU-x-icu")

strpos(
  lower(d.name COLLATE "ru-RU-x-icu"),
  lower(CAST(:search AS text) COLLATE "ru-RU-x-icu")
) > 0
```

Это native-запросы в `DepartmentRepository`; проект уже привязан к PostgreSQL. Альтернатива — нормализованная колонка `name_normalized`, заполняемая Java, но она требует backfill и дублирования логики. Альтернатива с `citext` тоже зависит от locale и не решает поиск подстроки так же просто.

### 2. Лёгкий DTO для поиска

`searchByName` возвращает `List<DepartmentDto>` (`id`, `name`, `type`) вместо `DepartmentResponseDto`. Это исключает обращение к ленивым `children` и `parent`, убирает N+1 и уменьшает payload. Для combobox-а этого достаточно. Сортировка — `ORDER BY d.name COLLATE "ru-RU-x-icu", d.id`.

### 3. Гонка на уникальности

Проверка `existsByName` перед вставкой сохраняется для понятного сообщения, но не гарантирует инвариант при параллельных запросах. Функциональный индекс отклонит дубликат на уровне БД, а `GlobalExceptionHandler` преобразует `DataIntegrityViolationException` в `400` с русским сообщением. Это закрывает и гонку, и возможные обходы приложения.

### 4. Точечное обновление дерева после создания

```text
POST 201
  |
  +-- type === FACTORY? --> перезагрузить текущую страницу корня
  |
  +-- parentId задан? ----> если кэш детей родителя существует,
  |                         перезагрузить страницы 0..current и заменить
  |                         кэш без дублей
  |                         обновить hasChildren родителя в корне и кэшах
  |
  +-- иначе --------------> ничего не обновлять
```

Смена страницы корня и раскрытые узлы сохраняются. Если новый `FACTORY` оказался на другой странице, пользователь видит сообщение об успехе и может перейти к ней. Это соответствует выбранному варианту 2 и не требует угадывать страницу.

Альтернатива — полный сброс дерева (проще, но теряет контекст) или оптимистичная вставка (риск нарушить сортировку и пагинацию).

### 5. Combobox без UI-библиотеки

`ParentCombobox` — controlled-компонент:

- поиск с debounce 300 мс и `AbortController`;
- при открытии запрос с пустой строкой возвращает весь справочник;
- опции показывают имя и тип;
- выбор мышью и клавиатурой (ArrowUp/ArrowDown/Enter/Escape);
- клик вне закрывает список;
- состояния загрузки, пустого результата и ошибки с повтором;
- текст без выбранной опции не считается выбранным родителем.

Для доступности используются `role="combobox"`, `aria-expanded`, `aria-controls`, `role="listbox"`, `role="option"`, `aria-selected`.

### 6. Модальное окно и форма

- Отдельный `DepartmentCreateModal`, условный рендер из `DepartmentsPage`; при закрытии состояние формы сбрасывается.
- Порядок полей: «Название» → «Тип» → «Входит в состав».
- `FACTORY`: поле родителя очищается и блокируется. Остальные типы: родитель обязателен.
- Клиентская валидация: непустое имя (trim, максимум 255), выбранный тип, выбранный родитель для не-`FACTORY`.
- «Добавить» — зелёная, «Отмена» — красная; во время POST кнопка добавления недоступна.
- Закрытие: «Отмена», Esc, клик по overlay. Ошибка сервера оставляет окно открытым.
- После успеха `onCreated(created)` закрывает окно, показывает сообщение и запускает обновление.

### 7. API-слой

`src/services/departments.js` расширяется:

- `createDepartment({ name, type, parentId })` → `POST /api/v1/departments` с JSON;
- `searchDepartments(search, { signal })` → `GET /api/v1/departments/search-by-name?search=...`;
- общий `request` получает метод, тело и `signal`, сохраняет разбор `body.message` для ошибок.

## Risks / Trade-offs

- **ICU-коллация зависит от сборки PostgreSQL** → в текущем контейнере `ru-RU-x-icu` есть; при смене образа без ICU миграция упадёт. Mitigation: зафиксировать требование к образу и проверить precondition.
- **Функциональный индекс не помогает поиску по подстроке** → `strpos` делает seq scan. Для текущего объёма справочника это приемлемо; при росте можно добавить trigram-индекс.
- **Точечное обновление может не показать новый элемент, если он попал на другую страницу корня** → показываем сообщение об успехе; пользователь может перейти на нужную страницу.
- **Native SQL привязывает репозиторий к PostgreSQL** → проект уже использует PostgreSQL и специфичную для него миграцию; альтернатива с нормализованной колонкой сложнее.
- **Одновременное создание** → индекс и обработчик `DataIntegrityViolationException` дают корректный `400`, а не `500`.
- **Дубликаты, различающиеся только регистром, уже могли существовать** → precondition остановит миграцию; перед применением нужно проверить и разрешить конфликт вручную.
