# Design

## Context

См. `proposal.md` — Why. Ниже только состояние и ограничения, которые влияют на решение.

- Фронтенд: CRA + React 19, JavaScript, без роутера, стейт-менеджера и UI-библиотеки. `src/App.js` — заглушка, каталогов `components/Departments`, `components/Layout`, `services` ещё нет. Тестовых файлов ноль, но `@testing-library/*` установлены.
- Существующая спека `department-catalog` описывает таблицу, дерево и боковое меню, но не описывает пагинацию и легенду. Её формулировка «корневые узлы (без родителя)» расходится с задачей «сначала только `FACTORY`».
- Бэкенд лежит рядом: `D:\IDEA_projects\metrology-app`, ветка `feature/11-find-all-epartment-by-pageable`. Локальный working copy содержит незакоммиченные доработки, а GitHub-ветка — нет.

### Состояние бэкенда

| Возможность | `origin/feature/11` (GitHub) | локальный working copy |
|---|---|---|
| `GET /all-by-type` (page, size, type, sortBy) | есть | есть |
| `GET /by-parent` (parentId, page, size, sortBy) | **нет** | есть (uncommitted) |
| поле `hasChildren` в ответе | **нет** | есть (uncommitted) |
| CORS для `http://localhost:3000` | **нет** | есть (`CorsConfig`, untracked) |

Контракт целевых эндпоинтов (локальное состояние):

```text
GET /api/v1/departments/all-by-type?page=0&size=10&type=FACTORY&sortBy=ASC
GET /api/v1/departments/by-parent?parentId=1&page=0&size=10&sortBy=ASC
```

Оба возвращают Spring `Page`:

```json
{
  "content": [
    {
      "id": 1,
      "name": "Завод «ЭлектронПрибор»",
      "type": "FACTORY",
      "parent": null,
      "children": [],
      "hasChildren": true
    }
  ],
  "number": 0,
  "size": 10,
  "totalElements": 25,
  "totalPages": 3,
  "first": true,
  "last": false
}
```

Особенности контракта:

- `page` нулевой; `size`, `page`, `type`, `sortBy` обязательны.
- `sortBy` — это **направление**, `ASC` или `DESC`; сортировка всегда по `name`, затем `id`.
- `children` в постраничных ответах всегда пустой; наличие детей определяется только `hasChildren`.
- `parent` — `{ id, name, type }` или `null`; этого достаточно для колонки «Родительское подразделение».
- Ошибки валидации бэкенд отдаёт как `400` с `{ message, status, timestamp }`.
- Типы: `FACTORY`, `WORKSHOP`, `AREA`, `LABORATORY`. Тестовое дерево: завод → цеха → лаборатории.

## Goals / Non-Goals

**Goals:**

- Показать корневой список только `FACTORY` с серверной пагинацией.
- Раскрывать дочерние узлы лениво, по «+», на любую глубину и для любого типа.
- Хранить состояние дерева и пагинации предсказуемо: без повторных запросов при повторном раскрытии.
- Показать легенду и понятные состояния загрузки, пустоты и ошибки.
- Сделать слой API, пригодный для переиспользования другими экранами.

**Non-Goals:**

- CRUD департаментов (создание, редактирование, удаление) — в задаче не требуется.
- Поиск по имени и произвольные фильтры, кроме `type=FACTORY` на корне.
- Реализация бэкенда: считаем, что нужные эндпоинты уже есть.
- Полноценные экраны «Приборы» и «Сотрудники»; максимум — заглушки из спеки, если это войдёт в scope.
- Синхронизация раскрытого состояния с URL или сохранение между перезагрузками.

## Decisions

### 1. Двухуровневая пагинация вместо одной глобальной

Дерево нельзя листать одной нумерацией страниц: строки разных родителей перемешаны, а дети ещё не загружены.

```text
Корневая страница (FACTORY, page=0..N)
        |
        +-- [Завод A] [+] --клик--> страница детей A (parentId=A, page=0..M)
        |                              |
        |                              +-- [Цех A1] [+] --клик--> страница детей A1
        |
        +-- [Завод B] [+]
```

Решение:

- Для корня — обычные элементы пагинации (`< 1 2 3 >`) и серверный `page`.
- Для детей — загрузка первой страницы при раскрытии и кнопка «Показать ещё» под детьми, если `last === false`.
- Размер страницы задаётся константой (предлагаю 10; обсуждаемо) и передаётся в оба запроса.

Альтернативы:

- Грузить всех детей узла целиком (`size=1000`) — проще, но не соответствует требованию постраничного вывода и плохо масштабируется.
- Пагинировать всё дерево на клиенте после загрузки — противоречит серверной пагинации и требует загружать весь каталог.
- Отдельная нумерация страниц внутри каждого узла — перегружает UI; «Показать ещё» достаточно.

### 2. Модель состояния

```text
rootPage:
  items: Department[]
  number: number
  totalPages: number
  loading: boolean
  error: string | null

expanded: Set<departmentId>

childrenByParent: {
  [parentId]: {
    items: Department[]
    page: number          // последняя загруженная страница
    totalPages: number
    loading: boolean
    error: string | null
  }
}
```

Правила:

- Раскрытие узла: если кэша нет — запрос первой страницы; если есть — только переключение `expanded`.
- «Показать ещё»: запрос `page + 1`, результаты добавляются в `items` (дедупликация по `id`).
- Сворачивание не удаляет кэш; повторное раскрытие не делает запрос.
- При смене корневой страницы раскрытые узлы, которых нет на странице, остаются в `expanded`, но не рендерятся. Кэш не сбрасывается; это безопасно, потому что `id` стабильны.
- Ошибка запроса детей показывается внутри узла с кнопкой «Повторить»; ошибка корня — блоком над таблицей.

Альтернатива: хранить плоский список строк и флаг `expanded` в каждой строке. Проще для рендера, но хуже для пагинации и повторных запросов; выбранная модель ближе к источнику данных.

### 3. Рендер дерева

- Из `rootPage.items` и `childrenByParent` строится плоский список видимых строк с `depth`.
- Отступ — `depth * 24px` (значение уточняется в CSS).
- Кнопка «+»/«−» рендерится только при `hasChildren === true`; у листа — пустой placeholder той же ширины, чтобы колонки не съезжали.
- Кнопка получает `aria-expanded` и доступное имя («Раскрыть дочерние подразделения» / «Свернуть»).
- Колонки: «Название», «Тип», «Родительское подразделение». Для корня родитель — «—».
- `children` из ответа не используется для определения наличия детей.

Альтернатива: рекурсивные компоненты `TreeNode`. Дают чистую вложенность, но усложняют пагинацию внутри узла; плоский список с `depth` проще и предсказуемее.

### 4. Слой API

- Целевой бэкенд — локальное состояние ветки `feature/11-find-all-epartment-by-pageable`: `/by-parent`, `hasChildren` и `CorsConfig`. CORS-конфигурация входит в change и коммитится вместе с доработками бэкенда. CRA-proxy не используем, чтобы не поддерживать два механизма доступа к API.
- `src/services/departments.js` (или `.js` с именованными функциями): `fetchRootPage({ page, size, sortBy })`, `fetchChildrenPage({ parentId, page, size, sortBy })`.
- Оба используют `URLSearchParams`, проверяют `response.ok` и достают `message` из тела ошибки.
- Базовый URL: `process.env.REACT_APP_API_BASE_URL` со значением по умолчанию `http://localhost:8080`.
- Константы `DEPARTMENT_TYPES`, `ROOT_TYPE = 'FACTORY'`, `PAGE_SIZE` — в отдельном модуле, чтобы не дублировать строки.

### 5. Легенда

Рекомендация: цветные бейджи типов с русскими названиями плюс подсказка.

```text
+------------------------------------------------------------------+
| Легенда:  [Завод]  [Цех]  [Участок]  [Лаборатория]               |
| Показаны заводы. Нажмите «+», чтобы раскрыть подразделения.      |
+------------------------------------------------------------------+
```

Альтернативы: хлебные крошки текущего пути (требуют знания цепочки предков) или только текстовая подпись. Окончательный вариант — в Open Questions.

### 6. Загрузка, пустота, ошибка

- Корень: скелетон/спиннер в таблице; при пустом `content` — «Департаменты не найдены»; при ошибке — текст и «Повторить».
- Дети: строка-заглушка «Загрузка…» под родителем; при пустом ответе — «Нет дочерних подразделений»; при ошибке — «Не удалось загрузить» + «Повторить».
- Ошибка одной ветки не ломает остальную таблицу.

### 7. Тесты

- `services/departments.test.js`: формирование URL, разбор успешного ответа, разбор `400`.
- Компонент таблицы: корневая пагинация, появление «+» по `hasChildren`, раскрытие/сворачивание, «Показать ещё», ошибка и повтор.
- Для тестов — мок `fetch`; внешних зависимостей не добавляем.

### 8. Scope приложения

Так как `App.js` — заглушка, таблице нужна страница. Предлагаю в этот change включить минимальный layout и боковое меню из спеки (`Департаменты`, `Приборы`, `Сотрудники` + заглушка «Появится скоро»). Альтернатива — только страница департаментов без навигации; тогда спека останется частично нереализованной. Решение — в Open Questions.

## Risks / Trade-offs

- **GitHub-ветка без `/by-parent`, `hasChildren` и CORS** → ленивое раскрытие и «+» без доработок невозможны. Mitigation: целевой контракт — локальное состояние; закоммитить изменения вместе с `CorsConfig`. CRA-proxy больше не рассматриваем.
- **Семантика «FACTORY vs корень»** → если у `FACTORY` появится родитель, он всё равно попадёт в корневой список. Mitigation: зафиксировать в спеке, что стартовый уровень определяется типом, а не отсутствием родителя.
- **Много раскрытых узлов = много запросов** → каждый узел грузится отдельно. Mitigation: ленивость, кэш, страницы по 10, отсутствие повторных запросов при сворачивании/раскрытии.
- **Некорректные `page`/`size`** → бэкенд может вернуть `400` или `500`. Mitigation: клиентские ограничения (`page >= 0`, `size` из фиксированного набора).
- **CORS** → без настройки запросы из dev-сервера не пройдут. Mitigation: `CorsConfig` в локальном бэкенде, коммитится вместе с доработками ветки.
- **Spring `Page` в JSON** → фронт зависит от полей `content/number/totalPages/last`; при смене сериализации возможны поломки. Mitigation: изолировать разбор в сервисе и покрыть тестом.
- **Спека расходится с задачей** → реализация может закрепить неверное поведение. Mitigation: delta-спека перед реализацией.
- **Нет тестовой базы** → регрессии невидны. Mitigation: начать с тестов сервиса и ключевого сценария раскрытия.

## Open Questions

Эти вопросы меняют спеку, подход или разбиение задач, поэтому `specs` и `tasks` намеренно не создаются до их решения.

1. **Легенда**: расшифровка типов, текущий путь или подсказка о раскрытии? Рекомендация — бейджи типов + подсказка.
2. **Пагинация детей**: «Показать ещё» внутри узла или загрузка всех детей сразу? Рекомендация — «Показать ещё».
3. **Scope**: включать ли layout и боковое меню из спеки или ограничиться таблицей департаментов? Рекомендация — включить.
4. **Размер страницы**: 10 по умолчанию или другой? Можно решить при разбиении задач.
5. **Сортировка**: нужен ли пользователю переключатель `ASC/DESC` или фиксируем `ASC`? Можно решить позже.
