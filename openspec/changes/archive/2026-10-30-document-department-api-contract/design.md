# Design

## Context

См. `proposal.md` — Why. Сейчас контракт API задан реализацией:
`src/services/departments.js` и `DepartmentController.java`. OpenSpec бэкенда
существует, но его `specs/` пуст. Change `add-department-deletion` добавляет
`deletion-check` и целевую семантику DELETE (`204`). Настоящий change создан
до его архивации: контракт фиксируется как целевой, а реализация удаления
отслеживается в `add-department-deletion`.

## Goals / Non-Goals

**Goals:**

- Зафиксировать контракт API в объёме, который реально использует UI.
- Связать репозитории через store, не копируя детальный контракт.
- Отделить архитектурную документацию от поведенческих спек.

**Non-Goals:**

- Описывать внутреннее устройство бэкенда, JPA-связи и классы.
- Дублировать полный OpenAPI-контракт во фронтенд-репозитории.
- Менять runtime-код.

## Decisions

### 1. Тонкая consumer-спека во фронтенде

`department-api` описывает только то, на что опирается UI: пути, параметры,
формы ответов и коды. Детальный контракт остаётся в бэкенде.

Альтернатива — полный контракт во фронте — отклонена: он быстро устареет и
создаст второй источник истины.

### 2. Store + references вместо копирования

Бэкенд регистрируется как `metrology-backend`, в конфиге указывается
`references: [metrology-backend]`. Инструкции артефактов получают read-only
индекс спеков бэкенда, а не их содержимое.

Альтернатива — git submodule или ручная синхронизация — отклонена как более
хрупкая.

### 3. Архитектура — отдельный документ

`docs/architecture.md` описывает слои, потоки данных и интеграцию.
`design.md` остаётся документом конкретного change и уходит в архив.

### 4. Контекст в config.yaml — только ограничения

В `context` попадают правила, которые нельзя вывести из кода: расположение
бэкенда, формат ошибок, требование парного change. Общая архитектура туда не
переносится.

## Risks / Trade-offs

- **Спека бэкенда пока пуста** → индекс store пуст; тонкая спека остаётся
  основным описанием ожиданий UI. Mitigation: завести capability в бэкенде.
- **`deletion-check` ещё не реализован** → спека описывает целевое поведение.
  Mitigation: реализация и приёмка идут в `add-department-deletion`; до его
  завершения спека не считается подтверждённой кодом.
- **Утечка Spring `Page` в контракт** → смена формата страницы затронет UI.
  Mitigation: зафиксировать поля страницы в спеке и тестах сервиса.
- **Расхождение с реальным бэкендом** → спека проверяется по контроллеру и
  тестам при каждом изменении API.

## Migration Plan

1. Зарегистрировать store и обновить `config.yaml`.
2. Добавить `docs/architecture.md` и ссылки в `AGENTS.md`.
3. Создать change и спеку `department-api`.
4. После ревью архивировать change.
5. Завести capability `department-api` в OpenSpec бэкенда.
