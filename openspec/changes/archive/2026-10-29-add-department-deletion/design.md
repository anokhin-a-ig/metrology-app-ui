# Design

## Context

См. `proposal.md` — Why. Ниже только состояние и ограничения, влияющие на подход.

- Таблица строится плоским списком строк с `depth` в `DepartmentTable.js:3`; колонок три, `StatusRow` использует `colSpan={3}` (`DepartmentTable.js:73`). Строки детей и корня рендерятся одним и тем же кодом, поэтому одно действие в строке покрывает все уровни.
- Страница владеет состоянием: `loadRoot` (`DepartmentsPage.js:42`), `refreshChildren` (`DepartmentsPage.js:111`), `markParentHasChildren` (`DepartmentsPage.js:169`). Модалка создания сама вызывает API и отдаёт результат странице через `onCreated` (`DepartmentCreateModal.js:99`) — этот же паттерн подходит для удаления.
- Сервис `request()` (`services/departments.js:5`) всегда вызывает `response.json()` (`services/departments.js:40`). Для DELETE это риск: успех может прийти с пустым телом или телом `"123"`.
- В приложении включён `React.StrictMode` (`src/index.js:8`), поэтому таймер и отправка DELETE должны быть защищены от двойного срабатывания в dev.
- Бэкенд уже принимает `DELETE /api/v1/departments/{id}` (`DepartmentController.java:167`). Удаление блокируется, если у департамента есть дети (`DepartmentDtoService.java:74`). Дополнительно на департамент ссылаются `Employee.department` и `Measurement.departmentOwner` (`Employee.java:38`, `Measurement.java:73`), внешние ключи объявлены без каскада (`01-init-db-table-changelog.xml:92`). Общая ошибка нарушения целостности сейчас превращается в `400` с текстом «Не удалось удалить департамент».
- Проверить сотрудников и измерения из UI сейчас нечем: `EmployeeController` умеет только создание, репозитория измерений нет. Поэтому для полноценного варианта A нужен отдельный read-only эндпоинт проверки.
- Durable-спека `openspec/specs/department-catalog/spec.md` в рабочем дереве отсутствует (staged deletion), но есть в `HEAD`. Дельта этого change добавляет требования; перед archive базовую спеку нужно восстановить.

Принято: вариант A (блокировать и объяснять) и предварительная проверка через новый эндпоинт. Если эндпоинт недоступен, UI деградирует до известного `hasChildren` и обработки ошибки DELETE.

## Goals / Non-Goals

**Goals:**

- Дать безопасное удаление с подтверждением именем и реальной отменой до отправки запроса.
- Не отправлять DELETE для заведомо зависимого департамента и объяснять причину.
- Сохранить корректными дерево, пагинацию, кэш детей и `hasChildren` после удаления.
- Сделать модалку доступной с клавиатуры и не ломать остальную таблицу ошибкой удаления.

**Non-Goals:**

- Каскадное удаление поддерева, мягкое удаление/корзина, массовое удаление.
- UI переназначения сотрудников и измерений.
- Изменение семантики DELETE на бэкенде (кроме проверки зависимостей и текстов ошибок).
- Общий рефакторинг модалок и полноценный focus-trap; в этом change модалка удаления повторяет паттерн `DepartmentCreateModal`.

## Decisions

### 1. Действие в отдельной колонке «Действия»

`DepartmentTable` получает `onDelete(department)`, в каждой строке типа `department` появляется кнопка «Удалить» с `aria-label="Удалить департамент <name>"`. `StatusRow` меняет `colSpan` на 4.

Альтернативы: иконка-корзина без текста — хуже discoverability и локализация; удаление по клику на строку — конфликтует с раскрытием и опасно.

### 2. Модалка владеет сценарием, страница — данными

Новый `DepartmentDeleteModal` получает `department`, `onClose`, `onDeleted`, `onShowChildren` и сам выполняет проверку, отсчёт и DELETE. Страница хранит только `deleteTarget` и обновляет списки после `onDeleted` — как `handleCreated` в `DepartmentsPage.js:204`.

Состояния:

```
checking --> blocked --(закрыть)--> closed
   |
   +--> confirm --(клик "Удалить")--> countdown --(5 c)--> deleting --(200)--> closed + refresh
          ^                              |                     |
          |                              | Отмена              | ошибка
          +------------------------------+                     v
          |                                                   error --(Повторить)--> countdown
          +------------------(X / Esc / оверлей)--------------+--> closed
```

- `checking` — только когда `hasChildren === false`: показываем «Проверка возможности удаления…».
- Если `hasChildren === true`, сразу `blocked` с причиной «есть дочерние подразделения»; фоновую проверку можно не делать.
- `confirm`: поле ввода, кнопка неактивна до совпадения; X/Esc/оверлей закрывают без запроса.
- `countdown`: ввод заблокирован, показан кружок и «Отменить удаление»; «Отмена» возвращает в `confirm` с сохранённым текстом, X/Esc/оверлей закрывают и отменяют отсчёт.
- `deleting`: закрытие и отмена недоступны, пока не пришёл ответ.
- `error`: сообщение, «Повторить» (новый отсчёт) и «Закрыть».

Альтернатива: держать всё состояние на странице. Отвергнута: разрастается `DepartmentsPage`, а модалка создания уже задаёт локальный паттерн.

### 3. Предварительная проверка зависимостей

Новый контракт:

```text
GET /api/v1/departments/{id}/deletion-check

200 OK
{
  "canDelete": false,
  "blockers": [
    { "type": "CHILDREN",    "count": 3  },
    { "type": "EMPLOYEES",   "count": 12 },
    { "type": "MEASUREMENTS","count": 0  }
  ]
}
```

`blockers` оставляет место новым зависимостям. UI показывает только ненулевые причины; коды переводятся в русский текст на клиенте.

Бэкенд:

- `DepartmentController` — read-only `GET /{id}/deletion-check`.
- `DepartmentDtoService.checkDeletion(id)` — existence + подсчёты.
- Репозитории: количество детей, сотрудников и измерений по `departmentId`; для измерений, вероятно, потребуется новый `MeasurementRepository`.
- `GlobalExceptionHandler` — различать `FK_EMPLOYEE_ON_DEPARTMENT` и `FK_MEASUREMENT_ON_DEPARTMENT_OWNER` и отдавать точные сообщения вместо общего «Не удалось удалить департамент».

Если эндпоинт вернул `404`/`501` или сеть недоступна, модалка не блокирует навсегда: использует `hasChildren` и разрешает попытку, а ошибку DELETE показывает как обычно. Сервер остаётся источником истины: проверка — UX-оптимизация, а не гарантия.

Альтернативы: расширить списочный DTO полями `canDelete`/`blockers` — данные стареют к клику и требуют агрегатов на каждую страницу; не проверять сотрудников/измерения — пользователь узнаёт о блокировке только после 5 секунд.

### 4. Отсчёт — реальная задержка перед DELETE

Пять секунд — это время, в течение которого запрос ещё не отправлен. Только так «Отменить удаление» честно отменяет действие.

- `DELETE_COUNTDOWN_SECONDS = 5` в `services/constants.js`.
- Дедлайн `Date.now() + 5000`, интервал ~100–250 мс; оставшиеся секунды вычисляются от дедлайна, а не уменьшением счётчика.
- Интервал очищается при закрытии и размонтировании; `firedRef` защищает от повторной отправки в StrictMode.
- Кружок — SVG-кольцо с числом секунд; при `prefers-reduced-motion` остаётся число без анимации.
- `role="timer"` на числе; старт и завершение объявляются через `aria-live`, без озвучивания каждой секунды.

Альтернативы: отправить DELETE сразу, а 5 секунд показывать как анимацию — отмена становится ложной; удержание кнопки — не то, что просит задача.

### 5. Совпадение имени

Сравнение: `input.trim() === department.name`, с учётом регистра. Кнопка выключена, пока условие не выполнено; форма дополнительно проверяет условие в `onSubmit`, чтобы Enter не обходил блокировку. Длинные имена и «ёлочки» внутри названия выводятся жирным текстом, без внешних кавычек.

Альтернатива: сравнение без учёта регистра — дружелюбнее, но слабее как барьер; можно пересмотреть после первого UX-фидбека.

### 6. Сервис и разбор ответа DELETE

- `deleteDepartment(id)` — `request('/api/v1/departments/<id>', { method: 'DELETE' })`.
- `request` меняется minimally: при `204` возвращает `null`; при `200` пытается `json()`, а при пустом/не-JSON теле возвращает `null`. Это сохраняет существующие моки, которые реализуют только `json()`.
- `fetchDeletionCheck(id)` — GET; ошибка получает `status`, чтобы отличать `404`/`501` (fallback) от прочих ошибок.
- Текст ошибки по-прежнему берётся из `{ message }`; если его нет — общий текст с кодом.

Альтернатива: отдельный «сырой» запрос для DELETE. Отвергнута: дублирование логики ошибок.

### 7. Обновление состояния после удаления

```
DELETE 200
   |
   +-- корневая строка --> loadRoot(pageNumber)
   |                          |
   |                          +-- content пуст и pageNumber > 0
   |                                --> переход на pageNumber - 1
   |
   +-- дочерняя строка --> refreshChildren(parentId)
                              |
                              +-- items пусто и last
                                    --> hasChildren(parent) = false
```

- Корень: перезапрос текущей страницы; если сервер вернул пустой `content` при `pageNumber > 0`, страница переключается на предыдущую. Чтобы не мигать пустым состоянием, `loadRoot` при таком ответе сам инициирует загрузку предыдущей страницы.
- Ребёнок: `refreshChildren(parentId)` уже перезапрашивает все загруженные страницы родителя и пересобирает `items` без дублей — это заодно выравнивает серверную пагинацию. После обновления, если `items.length === 0 && last`, флаг родителя сбрасывается.
- `markParentHasChildren` расширяется до установки значения (`true`/`false`), чтобы убирать «+» у опустевшего родителя.
- У удалённого узла очищаются `childrenByParent[deletedId]` и `expanded`, даже если сейчас они пусты.
- Успех: закрыть модалку, показать `departments__success` с именем, вернуть фокус на таблицу/следующую строку.

Альтернатива: локально вырезать строку. Отвергнута: ломает `totalPages`, `last` и `hasChildren`, особенно при удалении последнего элемента страницы.

### 8. Блокировка и подсказка

В `blocked` показываются причины и количества, если они есть. Если блокируют дети, доступна кнопка «Показать дочерние»: модалка закрывается, страница раскрывает узел и при необходимости загружает детей через существующий `handleToggle`. Для сотрудников/измерений действия переназначения нет — только объяснение и закрытие.

### 9. Тесты

- Сервис: метод/URL DELETE, `204`, пустое тело, `"123"`, извлечение `message`, `deletion-check` и его `status`.
- Модалка: fake timers; неактивная кнопка до совпадения; ровно один DELETE после 5 секунд; отмена не вызывает fetch; X/Esc; blocked; checking/fallback; error/retry; StrictMode.
- Страница: удаление корня, удаление ребёнка, пустая последняя страница, сброс `hasChildren`, сообщение об успехе, колонка действий.
- Бэкенд: `deletion-check` для детей/сотрудников/измерений; точные тексты FK-ошибок.
- Проверки: `npm test -- --watchAll=false`, `npx eslint src`, `npm run build`.

## Risks / Trade-offs

- **Эндпоинт проверки требует работы в бэкенде** → UI можно выпустить с fallback на `hasChildren` + ошибку DELETE; эндпоинт добавляется отдельно и не ломает контракт списка.
- **Проверка и удаление не атомарны** → между ними может появиться зависимость. Mitigation: серверная ошибка DELETE показывается как причина блокировки; после неё список обновляется.
- **Устаревший `hasChildren`** → проверка на сервере ловит реальное наличие детей; ошибка DELETE также маппится в blocked.
- **Пять секунд раздражают при частом удалении** → это требование задачи; длительность вынесена в константу и может быть изменена без переписывания логики.
- **StrictMode / двойной таймер** → дедлайн + интервал + `firedRef`; тест в StrictMode.
- **Зависший DELETE** → пока запрос в полёте, окно не закрывается. Mitigation: таймаут запроса (например, 15 с) с переходом в `error`; иначе пользователь ждёт ответа сети.
- **Много загруженных страниц детей** → `refreshChildren` делает несколько запросов. При размере 10 и небольшом дереве приемлемо; точечная правка массива отвергнута из-за пагинации.
- **Удаление в фоновой вкладке** → отсчёт по дедлайну может сработать при возврате. Это осознанный выбор; пауза по `visibilitychange` — возможное улучшение.
- **Durable-спека отсутствует** → до archive восстановить `openspec/specs/department-catalog/spec.md` из `HEAD`/архива, иначе новые требования не сольются с существующими.
- **Ответ DELETE `200 "123"`** → клиент не зависит от тела; в бэкенде желательно перейти на `204 No Content`.

## Migration Plan

1. Бэкенд: добавить `deletion-check`, подсчёты зависимостей и точные FK-сообщения; существующий DELETE не меняется.
2. UI: выпустить действие, модалку и обновление списков. При отсутствии эндпоинта работает fallback.
3. Проверить сценарии на тестовом дереве: лист, узел с детьми, департамент с сотрудником, последняя страница.
4. Перед archive восстановить durable-спеку `department-catalog` и убедиться, что дельта сливается с существующими требованиями.

Откат: удалить действие из таблицы; эндпоинт проверки остаётся безвредным. Миграций БД нет.

## Open Questions

- Нужно ли приостанавливать отсчёт, когда вкладка скрыта, или допустимо, что удаление сработает при возврате? По умолчанию — не приостанавливать, считать по дедлайну.
- Показывать ли количества зависимостей в blocked-состоянии всегда или только когда сервер их вернул? По умолчанию — показывать, если пришли.
