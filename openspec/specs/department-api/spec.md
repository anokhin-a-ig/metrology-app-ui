# department-api Specification

## Purpose

Описывает REST-контракт каталога департаментов, на который опирается
веб-интерфейс метрологии, чтобы фронтенд и бэкенд проверялись против одного
набора требований.

## Requirements

### Requirement: Постраничная загрузка корневых департаментов

Интерфейс SHALL получать корневые департаменты запросом
`GET /api/v1/departments/all-by-type` с параметрами `page`, `size`, `type`,
`sortBy` и использовать ответ как страницу Spring `Page`.

#### Scenario: Успешная загрузка страницы

- **WHEN** интерфейс запрашивает корневые департаменты с `type=FACTORY`
- **THEN** ответ содержит `content`, `number`, `size`, `totalElements`, `totalPages`, `first`, `last`

#### Scenario: Пустая страница

- **WHEN** на запрошенной странице нет департаментов
- **THEN** `content` пуст, а `totalElements` и `totalPages` согласованы с фактическим количеством

### Requirement: Загрузка дочерних департаментов

Интерфейс SHALL получать дочерние департаменты запросом
`GET /api/v1/departments/by-parent` с `parentId`, `page`, `size`, `sortBy`
и SHALL использовать признак `hasChildren` для показа возможности раскрытия.

#### Scenario: Раскрытие узла с детьми

- **WHEN** пользователь раскрывает департамент, у которого `hasChildren = true`
- **THEN** интерфейс запрашивает страницу дочерних с его `id` в `parentId`

#### Scenario: Узел без детей

- **WHEN** у департамента `hasChildren = false`
- **THEN** запрос дочерних не выполняется и элемент раскрытия не показывается

### Requirement: Создание департамента

Интерфейс SHALL создавать департамент запросом `POST /api/v1/departments`
с телом `{ name, type, parentId? }` и SHALL считать успехом ответ `201`.

#### Scenario: Создание корневого департамента

- **WHEN** пользователь отправляет имя и тип без `parentId`
- **THEN** бэкенд создаёт корневой департамент и возвращает `201` с созданным объектом

#### Scenario: Дубликат имени

- **WHEN** бэкенд возвращает `400` с сообщением о существующем имени
- **THEN** интерфейс показывает это сообщение в форме и не закрывает её

### Requirement: Поиск департаментов по имени

Интерфейс SHALL искать департаменты запросом
`GET /api/v1/departments/search-by-name` с параметром `search`
и SHALL отменять предыдущий запрос при вводе нового значения.

#### Scenario: Поиск с отменой предыдущего запроса

- **WHEN** пользователь продолжает ввод, пока предыдущий поиск ещё выполняется
- **THEN** предыдущий запрос отменяется, а результат показывается только для последнего значения

### Requirement: Удаление департамента и проверка зависимостей

Интерфейс SHALL удалять департамент запросом `DELETE /api/v1/departments/{id}`
и SHALL считать успехом `204` без тела. Перед удалением интерфейс SHALL
запрашивать `GET /api/v1/departments/{id}/deletion-check`.

#### Scenario: Успешное удаление

- **WHEN** бэкенд отвечает `204` на DELETE
- **THEN** интерфейс закрывает окно и обновляет затронутый список

#### Scenario: Департамент с зависимостями

- **WHEN** проверка возвращает `canDelete = false` со списком `blockers`
- **THEN** интерфейс блокирует удаление и показывает причины

#### Scenario: Проверка недоступна

- **WHEN** `deletion-check` отвечает `404` или `501`
- **THEN** интерфейс использует `hasChildren` и разрешает попытку DELETE с обработкой ошибки сервера

#### Scenario: Департамент уже удалён

- **WHEN** DELETE возвращает `404`
- **THEN** интерфейс сообщает об этом и обновляет список

### Requirement: Единый формат ошибок API

Интерфейс SHALL извлекать текст ошибки из поля `message` ответа
`{ message, status, timestamp }` и SHALL показывать общий текст, если тело
не является JSON или запрос завершился сетевой ошибкой.

#### Scenario: Ошибка с сообщением

- **WHEN** бэкенд возвращает `400` с телом `{ "message": "Департамент уже существует" }`
- **THEN** интерфейс показывает «Департамент уже существует»

#### Scenario: Ошибка без JSON

- **WHEN** ответ имеет не-2xx статус и тело не парсится как JSON
- **THEN** интерфейс показывает общий текст ошибки с кодом статуса
